### C0450 · k-idempotence · L2 · p
> Here's the classic distributed-systems trap. The producer sends a batch; the leader appends it; the acknowledgement gets lost on the way back (a timeout, a dropped connection). The producer can't tell "not written" from "written but not acknowledged", so it retries. Before Kafka 0.11 that meant a duplicate in the log: at-least-once delivery. The design docs compare it to inserting into a database table with an auto-generated key.

### C0465 · k-idempotence · L2 · p
> The broker only remembers the last 5 batches per producer per partition. So the producer must never have more than 5 unacknowledged requests on one connection. Otherwise a retry could refer to a batch the broker has already forgotten, and duplicate detection would fail. That's why idempotence requires max.in.flight.requests.per.connection ≤ 5 (default 5), plus retries > 0 and acks=all. And the producer docs promise that with idempotence on, ordering is preserved for any allowed value. The broker's refusal to accept sequence gaps is what makes that possible: a batch can't jump ahead of an earlier one that has to be retried.
- pass 1: ✅ ProducerConfig.java:271-276,339-343 — "broker only retains at most 5 batches"; "ordering preserved for any allowable value"
- pass 2: ✅ ProducerConfig.java:275-276 — "less than or equal to 5, because broker only retains at most 5 batches for each producer"; :341-343 "(with message ordering preserved for any allowable value)… retries > 0… acks must be 'all'"

### C0466 · k-idempotence · L2 · p
> Idempotence silently turns itself off if your configs conflict and you didn't enable it explicitly. The rule from the producer docs: idempotence is on by default "if no conflicting configurations are set". If you set acks=1 (or 0) or retries=0 without setting enable.idempotence, the producer logs one INFO line and disables idempotence, so retries can duplicate again. With enable.idempotence=true set explicitly, the same configs throw a ConfigException at start-up instead. Set it explicitly so a bad config fails loudly. (The in-flight limit is stricter: since 4.0, max.in.flight.requests.per.connection > 5 with idempotence enabled is always a ConfigException; there's no silent fallback any more.)
- pass 1: ✅ ProducerConfig.java:339-347,594-630; docs/getting-started/upgrade.md:283 — silent disable unless explicit; "no longer automatically fall back when… exceeds 5"
- pass 2: ✅ ProducerConfig.java:345-347 doc quote; :604-616 log.info("Idempotence will be disabled…") vs ConfigException when explicit; :621-622 in-flight > 5 always ConfigException; upgrade.md:283 (4.0.0) "no longer automatically fall back"
