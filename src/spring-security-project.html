Jak pracować z tym projektem

rozdział kursu → kod → test albo curl

Kurs pokazuje ataki i mechanizmy obrony. Tutaj masz jeden projekt, który zabezpieczasz warstwa po warstwie. Każde zadanie zaczyna się od linku do rozdziału kursu. Potem dopisujesz kod i sprawdzasz efekt: kodem odpowiedzi HTTP, nagłówkiem, logiem albo testem, który przechodzi.

Domena to NoteVault: prywatne notatki. Użytkownik zakłada konto, loguje się w przeglądarce i widzi tylko swoje notatki. Administrator widzi listę kont i może usunąć każdą notatkę. Od zadania 10 te same notatki czyta też klient zewnętrzny (aplikacja mobilna, integracja) z tokenem z Keycloaka. Prosta domena, a ma prawie wszystko, co da się zepsuć: hasła, sesje, CSRF, cudze dane pod zgadniętym ID i tokeny.

Własny SecurityFilterChain i zagadka 401 zamiast 403

API odpowiada kodem, a nie przekierowaniem
📖 Kurs: Łańcuch filtrów📖 401 vs 403
🧭 Po co to NoteVault

NoteVault to API dla własnego frontendu. Przekierowanie 302 na HTML-ową stronę logowania nic frontendowi nie da: fetch pójdzie za przekierowaniem i dostanie HTML zamiast JSON-a. API ma odpowiadać 401, gdy nie wie, kim jesteś, i 403, gdy wie, ale nie wolno ci.

🎯 Zadanie 2
  1. Utwórz SecurityConfig z beanem SecurityFilterChain. Sam fakt, że taki bean istnieje, wyłącza domyślny łańcuch Boota.
  2. Publiczny ma być tylko /actuator/health. Reszta wymaga logowania.
  3. Zostaw HTTP Basic (do testów z curl), ale jako entry point ustaw HttpStatusEntryPoint(UNAUTHORIZED).
  4. 💣 Wyślij curl -u user:pw -X POST localhost:8080/api/notes. Spodziewasz się 403 (brak tokenu CSRF, o tym w zadaniu 6), a dostajesz 401. Znajdź przyczynę i ją napraw.
✅ Jak sprawdzić

Bez logowania: 401, bez przekierowania i bez nagłówka WWW-Authenticate. /actuator/health: 200. POST z Basic, ale bez tokenu CSRF: 403, gdy /error jest publiczne, i 401, gdy nie jest. Tak to wyszło na projekcie referencyjnym.

🔑 Rozwiązanie
src/main/java/dev/notevault/security/SecurityConfig.java (wersja z zadania 2)
@Configuration
class SecurityConfig {

    @Bean
    SecurityFilterChain web(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/actuator/health", "/error").permitAll()
                .anyRequest().authenticated())
            .httpBasic(Customizer.withDefaults())
            .exceptionHandling(ex -> ex.authenticationEntryPoint(new HttpStatusEntryPoint(HttpStatus.UNAUTHORIZED)));
        return http.build();
    }
}

Dlaczego 401? CsrfFilter stoi w łańcuchu przed BasicAuthenticationFilter. Odrzuca żądanie, zanim ktokolwiek sprawdzi hasło, i ustawia błąd 403. Kontener servletów przekazuje wtedy żądanie do /error. Spring Security autoryzuje także ten przekazany request, a ty jesteś na nim wciąż anonimowy. /error wymaga logowania, więc entry point zamienia 403 na 401. Gdy /error jest publiczne, widzisz prawdziwy kod.

⚠️ Uwaga

Tę pułapkę zobaczysz jeszcze raz: błąd CSRF (403) bez publicznego /error wygląda jak „nie zalogowany”, bo CsrfFilter odrzuca żądanie, zanim użytkownik zostanie uwierzytelniony. Gdy kod odpowiedzi nie ma sensu, włącz DEBUG dla org.springframework.security i szukaj w logu drugiego przejścia przez łańcuch, tego dla /error.

🔑 Rozwiązanie
src/main/java/dev/notevault/account/UserAccounts.java (wersja z zadania 3)
@Service
public class UserAccounts implements UserDetailsService, UserDetailsPasswordService {

    private final JdbcUserDetailsManager users;
    private final PasswordEncoder encoder;

    UserAccounts(DataSource dataSource, PasswordEncoder encoder) {
        this.users = new JdbcUserDetailsManager(dataSource);
        this.encoder = encoder;
    }

    @Override
    public UserDetails loadUserByUsername(String username) {
        return users.loadUserByUsername(username);
    }

    @Override
    public UserDetails updatePassword(UserDetails user, String newPassword) {
        return users.updatePassword(user, newPassword);
    }

    public boolean exists(String username) {
        return users.userExists(username);
    }

    public void register(String username, String rawPassword, String... roles) {
        users.createUser(User.withUsername(username)
            .password(encoder.encode(rawPassword))
            .roles(roles)
            .build());
    }
}
src/main/java/dev/notevault/account/AccountController.java (fragment)
record Registration(@NotBlank @Pattern(regexp = "[a-z0-9_]{3,50}") String username,
        @NotBlank @Size(min = 12, max = 128) String password) {
}

@PostMapping("/api/register")
ResponseEntity<Void> register(@Valid @RequestBody Registration registration) {
    if (accounts.exists(registration.username())) {
        return ResponseEntity.status(HttpStatus.CONFLICT).build();
    }
    accounts.register(registration.username(), registration.password(), "USER");
    return ResponseEntity.status(HttpStatus.CREATED).build();
}

W SecurityConfig dopisz .requestMatchers(HttpMethod.POST, "/api/register").permitAll(). AdminBootstrap jest w projekcie referencyjnym. To ApplicationRunner, który wywołuje register("admin", hasło, "USER", "ADMIN"), gdy konta jeszcze nie ma.

❓ Nie ma głupich pytań
P:
Po co UserAccounts, skoro JdbcUserDetailsManager mógłby być beanem?
O:
Bo w zadaniu 8 dołożysz do loadUserByUsername blokadę konta. Spring Security sam podpina do logowania UserDetailsService tylko wtedy, gdy taki bean jest dokładnie jeden. Przy dwóch beanach tego typu nie wybiera żadnego. Jedna klasa-fasada omija ten problem.
P:
Po co UserDetailsPasswordService?
O:
Pozwala Springowi po udanym logowaniu przepisać hash na mocniejszy, gdy DelegatingPasswordEncoder uzna stary za przestarzały, na przykład {noop} albo {sha256}. JdbcUserDetailsManager już implementuje ten interfejs. Fasada tylko przekazuje wywołanie.

Notatki: cudza notatka pod zgadniętym ID

zalogowany to nie znaczy uprawniony

🧭 Po co to NoteVault

Notatka ma właściciela. Uwierzytelnienie mówi tylko, kim jest użytkownik. Nie mówi, czy wolno mu przeczytać notatkę numer 17. IDOR (Insecure Direct Object Reference) to sytuacja, w której wystarczy podmienić liczbę w URL, żeby czytać cudze dane.

Admin: reguły URL i @PreAuthorize

dwie warstwy autoryzacji
📖 Kurs: Reguły URL📖 Method security📖 Role i authorities
🧭 Po co to NoteVault

Admin ma widzieć listę kont i usuwać dowolne notatki, na przykład po zgłoszeniu nadużycia. Zwykły użytkownik usuwa tylko swoje. Pierwszą regułę da się wyrazić samym URL-em. Druga zależy od danych (kto jest właścicielem), więc należy do metody.

🎯 Zadanie 5
  1. W łańcuchu dodaj .requestMatchers("/api/admin/**").hasRole("ADMIN"), przed anyRequest(). Kolejność ma znaczenie: wygrywa pierwsza pasująca reguła.
  2. Dodaj GET /api/admin/users z dodatkowym @PreAuthorize("hasRole('ADMIN')") i włącz @EnableMethodSecurity.
  3. Dodaj DELETE /api/notes/{id}, który woła NoteService.delete. Na metodzie serwisu ustaw regułę: admin albo właściciel.
✅ Jak sprawdzić

Bob na /api/admin/users: 403. Admin: 200. Bob usuwa notatkę Alice: 403. Admin: 204. Testy: userWithoutAdminRoleGets403, adminSeesUsers, methodSecurityStopsDeletingSomeoneElsesNote, adminMayDeleteAnyNote.

🔑 Rozwiązanie
src/main/java/dev/notevault/notes/NoteService.java
@Service
public class NoteService {

    private final NoteRepository notes;

    NoteService(NoteRepository notes) {
        this.notes = notes;
    }

    /** Usunąć może właściciel albo admin. Reguła siedzi przy metodzie, więc obowiązuje każdego wołającego. */
    @PreAuthorize("hasRole('ADMIN') or @noteRepository.isOwner(#id, authentication.name)")
    public void delete(long id) {
        notes.delete(id);
    }
}

#id działa, bo parent Spring Boota kompiluje z flagą -parameters, więc nazwy parametrów są w bajtkodzie. @noteRepository to odwołanie do beana po nazwie.

❓ Nie ma głupich pytań
P:
Czemu kasowanie cudzej notatki daje tu 403, a czytanie 404?
O:
To świadomy wybór, który da się obronić. Przy odczycie właściciel siedzi w zapytaniu, więc ukrywasz istnienie notatki. @PreAuthorize rzuca AccessDeniedException, a to daje 403. Jeśli chcesz 404 także tutaj, sprawdź właściciela w zapytaniu DELETE … WHERE id = ? AND owner = ?, a regułę zostaw tylko dla admina.

Przeglądarka: logowanie, CSRF, sesje

Frontend loguje się formularzem, sesja trafia do Redisa, a bot zgadujący hasła trafia na blokadę.

Logowanie z SPA i token CSRF

ciasteczko sesji wymaga ochrony przed CSRF
📖 Kurs: CSRF📖 Sesje
🧭 Po co to NoteVault

Frontend NoteVault (index.html + app.js) loguje się raz i dalej trzyma sesję w ciasteczku. Przeglądarka dołącza to ciasteczko do każdego żądania pod ten adres, także do żądania wysłanego z cudzej strony. Token CSRF dowodzi, że żądanie przyszło z twojego frontendu.

🎯 Zadanie 6
  1. Zamień HTTP Basic na formLogin: loginProcessingUrl("/api/login"), sukces 204, porażka 401, bez przekierowań. Strona logowania to /.
  2. Dodaj logout pod /api/logout z HttpStatusReturningLogoutSuccessHandler.
  3. Włącz csrf(csrf -> csrf.spa()). Token trafia do ciasteczka XSRF-TOKEN, a frontend odsyła go w nagłówku X-XSRF-TOKEN.
  4. Dodaj GET /api/csrf (publiczny). Zanim frontend wyśle POST /api/login, woła ten adres, żeby dostać pierwszy token.
  5. Wrzuć index.html i app.js do src/main/resources/static i otwórz http://localhost:8080.
✅ Jak sprawdzić

Logowanie bez nagłówka X-XSRF-TOKEN: 403 (test loginWithoutCsrfTokenIsRejected). Z tokenem: 204, a /api/me zwraca twoją nazwę. Wylogowanie zwraca 200, bo tyle domyślnie odsyła HttpStatusReturningLogoutSuccessHandler. Potem /api/me daje 401 (test logoutEndsTheSession). Ten sam przepływ w curl:

     -d 'username=alice&password=alice-password-123' localhost:8080/api/login -o /dev/null -w '%{http_code}\n'
curl -s -b jar localhost:8080/api/me

// Spring Security (csrf.spa()) zapisuje token w ciasteczku XSRF-TOKEN; odsyłamy go w nagłówku X-XSRF-TOKEN.
function csrfToken() {
  const match = document.cookie.match(/(?:^|; )XSRF-TOKEN=([^;]*)/);
  return match ? decodeURIComponent(match[1]) : '';
}

async function api(method, url, body, form) {
  const headers = { 'X-XSRF-TOKEN': csrfToken() };
  if (body && !form) headers['Content-Type'] = 'application/json';
  return fetch(url, { method, headers, body: form ? body : body && JSON.stringify(body) });
}

Po co /api/csrf? Od Spring Security 6 token CSRF ładuje się leniwie. Ciasteczko powstaje dopiero wtedy, gdy coś po token sięgnie. Endpoint, który przyjmuje CsrfToken jako parametr, właśnie po niego sięga.

src/main/java/dev/notevault/account/LoginAttempts.java
@Component
public class LoginAttempts {

    static final int MAX_FAILURES = 5;
    static final Duration LOCK_TIME = Duration.ofMinutes(15);

    private final StringRedisTemplate redis;

    LoginAttempts(StringRedisTemplate redis) {
        this.redis = redis;
    }

    @EventListener
    void onFailure(AuthenticationFailureBadCredentialsEvent event) {
        String key = key(event.getAuthentication().getName());
        Long failures = redis.opsForValue().increment(key);
        if (failures != null && failures == 1) {
            redis.expire(key, LOCK_TIME);
        }
    }

    @EventListener
    void onSuccess(AuthenticationSuccessEvent event) {
        redis.delete(key(event.getAuthentication().getName()));
    }

    public boolean isLocked(String username) {
        String failures = redis.opsForValue().get(key(username));
        return failures != null && Integer.parseInt(failures) >= MAX_FAILURES;
    }

    private static String key(String username) {
        return "login-failures:" + username.toLowerCase();
    }
}

SecurityConfig.java: łańcuch extApi
/** Łańcuch 1: API dla klientów z tokenem JWT. Bez sesji i bez ciasteczek, więc bez CSRF. */
@Bean
@Order(1)
SecurityFilterChain extApi(HttpSecurity http) throws Exception {
    JwtAuthenticationConverter jwtConverter = new JwtAuthenticationConverter();
    jwtConverter.setPrincipalClaimName("preferred_username");
    jwtConverter.setJwtGrantedAuthoritiesConverter(new KeycloakRoles());

    http
        .securityMatcher("/ext/**")
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/ext/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .oauth2ResourceServer(rs -> rs.jwt(jwt -> jwt.jwtAuthenticationConverter(jwtConverter)))
        .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .csrf(csrf -> csrf.disable())
        .cors(Customizer.withDefaults());
    return http.build();
}
src/main/java/dev/notevault/security/KeycloakRoles.java
/** Keycloak trzyma role realmu w claimie realm_access.roles; Spring chce je jako ROLE_*. */
class KeycloakRoles implements Converter<Jwt, Collection<GrantedAuthority>> {

    @Override
    public Collection<GrantedAuthority> convert(Jwt jwt) {
        Map<String, Object> realmAccess = jwt.getClaimAsMap("realm_access");
        if (realmAccess == null || !(realmAccess.get("roles") instanceof List<?> roles)) {
            return List.of();
        }
        return roles.stream()
            .map(role -> (GrantedAuthority) new SimpleGrantedAuthority("ROLE_" + role.toString().toUpperCase()))
            .toList();
    }
}

❓ Nie ma głupich pytań
P:
Po co dwa łańcuchy? Nie wystarczy jeden z formLogin i oauth2ResourceServer?

🧩 Nowy komponent: Docker secrets i configtree
Co to
Sekcja secrets: w Compose montuje plik z hosta do kontenera pod /run/secrets/<nazwa>. Spring Boot czyta katalog takich plików przez spring.config.import=configtree:/run/secrets/: nazwa pliku staje się nazwą właściwości, a treść pliku jej wartością.
Po co
Hasło nie trafia do zmiennych środowiskowych, więc nie widać go w docker inspect ani w środowisku procesów potomnych. Nie ma go w obrazie, w repozytorium ani w compose.full.yaml.
Jak łączy
Secret montujesz pod nazwą właściwości, na przykład target: spring.datasource.password. Wtedy configtree mapuje go bez żadnych placeholderów. Końcowy znak nowej linii configtree obcina sam (opcja AUTO_TRIM_TRAILING_NEW_LINE).
🎯 Zadanie 12
  1. Napisz Dockerfile wieloetapowy: build na eclipse-temurin:21-jdk z cache'em Mavena (RUN --mount=type=cache), uruchomienie na eclipse-temurin:21-jre jako użytkownik bez roota. W .dockerignore wyklucz secrets/*.txt.
  2. Napisz secrets/generate.sh, który tworzy losowe hasła w secrets/*.txt z prawami 600. Dodaj secrets/*.txt do .gitignore.
  3. Napisz compose.full.yaml z czterema secretami. PostgreSQL czyta hasło z POSTGRES_PASSWORD_FILE. Redis i Keycloak nie obsługują zmiennych *_FILE, więc ich komenda startowa czyta plik przez sh -c.
  4. W aplikacji ustaw SPRING_CONFIG_IMPORT=configtree:/run/secrets/.
  5. 💣 Uruchom wszystko. Pobierz token z localhost:8180 i wyślij go do /ext/notes. Jeśli dostajesz 401, przeczytaj „Pułapkę issuera” niżej.

✅ Jak sprawdzić

W zmiennych środowiskowych kontenera aplikacji nie ma żadnego hasła:

$ docker inspect notevault-app-1 --format '{{range .Config.Env}}{{println .}}{{end}}' | grep SPRING
SPRING_CONFIG_IMPORT=configtree:/run/secrets/
SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_JWK_SET_URI=http://keycloak:8080/realms/notevault/protocol/openid-connect/certs
SPRING_DATASOURCE_URL=jdbc:postgresql://postgres:5432/notevault
SPRING_DATASOURCE_USERNAME=notevault
SPRING_DATA_REDIS_HOST=redis

$ docker compose -f compose.full.yaml exec app ls /run/secrets
notevault.admin.password  spring.data.redis.password  spring.datasource.password

W logu aplikacji pojawia się Admin account created, czyli hasło admina doszło z pliku. Redis bez hasła odpowiada NOAUTH Authentication required.

Sprawdziłem to tylko na Docker Desktop dla macOS. Tam pliki z prawami 600 są czytelne dla użytkownika app w kontenerze. Na Linuksie bind mount zachowuje właściciela z hosta, więc użytkownik o UID 10001 może nie mieć prawa odczytu. Wtedy dopasuj właściciela albo uprawnienia pliku do UID z Dockerfile.

⚠️ Pułapka issuera

Token pobrany na twoim komputerze z localhost:8180 ma "iss":"http://localhost:8180/realms/notevault". Kusi, żeby w kontenerze aplikacji ustawić issuer-uri=http://keycloak:8080/realms/notevault, bo tylko pod tym adresem aplikacja widzi Keycloaka. Wtedy każdy token odpada:

WWW-Authenticate: Bearer error="invalid_token", error_description="An error occurred while attempting to decode the Jwt: The iss claim is not valid", …

Rozwiązanie z projektu: rozdziel dwa adresy. jwk-set-uri wskazuje sieć Dockera (keycloak:8080), bo stamtąd aplikacja pobiera klucze. issuer-uri zostaje http://localhost:8180/…, bo z nim Spring porównuje claim iss. Keycloak dostaje KC_HOSTNAME=http://localhost:8180, więc wpisuje ten sam issuer także do tokenów pobranych z wnętrza sieci Dockera. KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true pozwala przy tym aplikacji łączyć się z nim pod keycloak:8080.

Druga niespodzianka z tego samego uruchomienia: po dodaniu KC_HOSTNAME Keycloak odrzucał żądanie tokenu z hosta błędem {"error":"invalid_request","error_description":"HTTPS required"}. Realm deweloperski ma więc "sslRequired": "none". W produkcji Keycloak stoi za HTTPS i tego ustawienia nie zmieniasz.

🔬 Głębiej (L3): co zamiast plików na produkcji

Docker secret w zwykłym Compose to plik na dysku hosta. Jest lepszy od zmiennej środowiskowej, ale ktoś musi ten plik położyć, chronić i podmieniać. W większym systemie hasła wydaje i rotuje osobna usługa, a aplikacja dostaje do niej dostęp przez swoją tożsamość, bez hasła startowego.

Kubernetes Secretobiekt w API klastra, montowany jako plik albo zmienna; w etcd szyfruj go „at rest” (najlepiej przez KMS)aplikacja i tak działa w Kubernetes; configtree czyta zamontowany katalog tak samo jak /run/secrets
HashiCorp Vault / OpenBaoserwer sekretów; umie wydawać dynamiczne hasła do bazy z krótkim TTL; w Springu przez Spring Cloud Vault i spring.config.import=vault://wiele usług, wymóg rotacji i audytu, środowisko poza jedną chmurą
Menedżer sekretów chmury (AWS Secrets Manager, Google Secret Manager, Azure Key Vault)zarządzana usługa z rotacją i logiem dostępu; aplikacja uwierzytelnia się rolą chmury (workload identity), np. Spring Cloud AWS: spring.config.import=aws-secretsmanager:…system działa w jednej chmurze

✏️ Dalej na własną rękę
  • Dodaj CompromisedPasswordChecker do rejestracji i logowania (kurs: Brute force). Ustaw timeout i zdecyduj, co robisz, gdy Have I Been Pwned nie odpowiada.
  • Wpuść frontend przez Keycloaka (Authorization Code + PKCE) zamiast własnego formularza (kurs: OAuth 2.0 / OIDC, Gdzie trzymać token).
  • Postaw Caddy albo nginx z HTTPS przed aplikacją, ustaw server.forward-headers-strategy i sprawdź, że pojawia się Strict-Transport-Security (kurs: HTTPS, HSTS i proxy).
  • Loguj zdarzenia logowania do audytu (kurs: Audyt i obserwowalność).
