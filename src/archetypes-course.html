Czym są archetypy oprogramowania?

To uniwersalne, gotowe rozwiązania dla problemów, które powtarzają się w każdym systemie. Pokażemy Ci, jak zamawianie taksówki, rezerwacja pokoju czy system windykacyjny sprowadzają się do tych samych, fundamentalnych klocków.

Dzięki archetypom jeszcze bardziej zajarasz się programowaniem! Zobaczysz wzór w chaosie i wreszcie przestaniesz tracić czas na poszukiwania OCZYWISTOŚCI.

Archetyp Party

Problem: Wieczny chaos z użytkownikami

Rozwiązanie: Raz modelujesz klienta indywidualnego, potem firmę, potem pracownika, a na końcu partnera biznesowego. Twój kod pęka od if-ów, a modele się rozjeżdżają.
Rozwiązanie: "Party". Zamiast tworzyć osobne klasy Client czy Partner, modelujesz uniwersalny Party i przypisujesz mu role. Ten sam sprawdzony model obsłuży Ci system bankowy, CRM, a nawet rezerwację wizyt u lekarza.

Interaktywny diagram Party Archetypu

Przykład w Javie

public class Party {
    private String id;
    private List<PartyRole> roles;
    private PartyType type;
    
    public enum PartyType {
        INDIVIDUAL, ORGANIZATION, EMPLOYEE, PARTNER
    }
    
    public enum PartyRole {
        CUSTOMER, EMPLOYEE, MANAGER, PARTNER
    }
    
    public void addRole(PartyRole role) {
        if (!roles.contains(role)) {
            roles.add(role);
        }
    }
    
    public boolean hasRole(PartyRole role) {
        return roles.contains(role);
    }
}

// Użycie
Party customer = new Party();
customer.addRole(PartyRole.CUSTOMER);
customer.addRole(PartyRole.MANAGER);
Konfiguracje: Bank CRM System medyczny

Archetyp Ordering

Problem: Każdy biznes to "inny" proces

Rozwiązanie: Wydaje Ci się, że sprzedaż ubezpieczeń, wysyłka paczki i spłata kredytu to trzy różne światy.
Rozwiązanie: "Ordering". Uświadomisz sobie, że niemal każdy biznes to sklep. Sprzedaje "produkt" (ubezpieczenie, usługę kurierską, kredyt) o pewnej "konfiguracji" (suma ubezpieczenia, rozmiar paczki, liczba rat) i "cenie". Gdy to zobaczysz, proces zamawiania, wyceny i płatności staje się jednym, uniwersalnym, dawno zaprojektowanym schematem.

Schemat Ordering

Przykład w Javie

public class OrderingProcess<T extends Product> {
    private T product;
    private Map<String, Object> configuration;
    private BigDecimal price;
    private Payment payment;
    
    public void configure(String key, Object value) {
        configuration.put(key, value);
    }
    
    public BigDecimal calculatePrice() {
        return product.getPrice(configuration);
    }
    
    public void processOrder() {
        validateOrder();
        PaymentResult result = payment.process(price);
        if (result.isSuccessful()) {
            completeOrder();
        }
    }
}

// Przykłady zastosowań
OrderingProcess<InsurancePolicy> insuranceOrder = new OrderingProcess<>();
insuranceOrder.configure("coverageAmount", 100000);

OrderingProcess<PackageItem> deliveryOrder = new OrderingProcess<>();
deliveryOrder.configure("weight", 5.2);

OrderingProcess<LoanProduct> loanOrder = new OrderingProcess<>();
loanOrder.configure("numberOfPayments", 24);

Archetyp Scheduling

Problem: Tworzysz złożony harmonogram

Rozwiązanie: Planujesz zadania na budowie, które zależą od siebie. Chwilę później projektujesz ścieżkę nauki nowej technologii. Dwa różne problemy?
Rozwiązanie: "Scheduling". Pod spodem to zawsze graf zależności. Gdy nauczysz się go modelować, dostaniesz narzędzie, które daje realną przewagę: ten sam kod ogarnia logistykę, edukację czy finanse. To jest właśnie myślenie abstrakcyjne w praktyce.

Graf zależności zadań

Przykład w Javie

public class TaskScheduler {
    private List<Task> tasks;
    private Map<String, List<String>> dependencies;
    
    public void addTask(Task task, List<String> dependsOn) {
        tasks.add(task);
        dependencies.put(task.getId(), dependsOn);
    }
    
    public List<Task> getExecutionOrder() {
        List<Task> ordered = new ArrayList<>();
        Set<String> completed = new HashSet<>();
        
        while (ordered.size() < tasks.size()) {
            Task next = tasks.stream()
                .filter(t -> !completed.contains(t.getId()))
                .filter(t -> canExecute(t))
                .findFirst()
                .orElseThrow(() -> new IllegalStateException("Circular dependency detected"));
            
            ordered.add(next);
            completed.add(next.getId());
        }
        
        return ordered;
    }
    
    private boolean canExecute(Task task) {
        return dependencies.getOrDefault(task.getId(), Collections.emptyList())
            .stream()
            .allMatch(completed::contains);
    }
}

Heurystyki rozpoznawania archetypów

🔍 Heurystyka Party:

Sprawdź czy system obsługuje różne typy podmiotów (klient, pracownik, partner) z podobnymi atrybutami - jeśli tak, prawdopodobnie potrzebujesz Party archetypu.

🔍 Heurystyka Ordering:

Zobacz czy proces biznesowy można podzielić na: produkt + konfigurację + wycenę + płatność - to klasyczny ordering.

🔍 Heurystyka Scheduling:

Jeśli tworzysz listę zadań z zależnościami między sobą, użyj scheduling archetypu.

🔍 Poziomy abstrakcji:

Archetypy działają na trzech poziomach: DDD (granice i język domeny), Architektura (skalowalność i elastyczność), Archetypy (gotowe receptury).

Interaktywny Quiz

W jakim przypadku można zastosować archetyp Party?
  • System zarządzania pracownikami, gdzie każdy pracownik ma różne role i uprawnienia
  • System faktur, gdzie potrzebujesz tylko jednej klasy Faktura
  • System rezerwacji pokoju hotelowego
  • System kolejkowania zamówień w sklepie internetowym

Dlaczego warto używać archetypów?

  • ✅ Oszczędność czasu - Nie musisz wynajdywać koła na nowo
  • ✅ Lepsza skalowalność - Gotowe wzorce zapewniają solidną bazę
  • ✅ Mniejsze ryzyko błędów - Wzorce zostały przetestowane w wielu projektach
  • ✅ Łatwiejsze utrzymanie - Klarowna struktura kodu
  • ✅ Szybszy czas rozwoju - Skup się na konkurencyjnej przewadze biznesowej
