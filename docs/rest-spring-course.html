Część I

HTTP: protokół, na którym wszystko stoi

Semantyka metod, statusów, nagłówków i cache. Tego Spring za ciebie nie zaprojektuje.

Żądanie i odpowiedź: tekst z regułami

wiadomość, nie wywołanie funkcji

HTTP to bezstanowy protokół typu żądanie-odpowiedź. Klient otwiera połączenie i wysyła wiadomość. Serwer odsyła wiadomość. Obie mają ten sam kształt: linia startowa, pola nagłówka, pusta linia, opcjonalna treść. Semantykę opisuje RFC 9110, cache RFC 9111, a format na łączu RFC 9112 (HTTP/1.1), RFC 9113 (HTTP/2) i RFC 9114 (HTTP/3). Dzięki temu podziałowi semantyka nie zmienia się między wersjami protokołu: zmienia się tylko sposób przesyłania bajtów.

Trzy rzeczy, które warto zapamiętać od razu. Host jest obowiązkowy w HTTP/1.1, bo pod jednym adresem IP żyje wiele serwisów. Content-Type opisuje treść, która właśnie leci, a Accept mówi, czego klient oczekuje z powrotem. Status to wynik semantyczny, który rozumieją proxy, cache i klienci, zanim ktokolwiek dotknie treści.

❓ Nie ma głupich pytań
Q:
HTTP jest „bezstanowy”, a przecież loguję się i mam sesję?
A:
Bezstanowy jest protokół: każda wiadomość jest zrozumiała sama w sobie. Sesja to stan aplikacji, który ciastko lub token tylko wskazuje lub niesie. Rozdział o REST pokaże, gdzie ten stan powinien mieszkać.
📌 W punktach
  • Wiadomość = linia startowa + nagłówki + pusta linia + treść.
  • Semantyka (RFC 9110) nie zależy od wersji HTTP.
  • Content-Type opisuje to, co wysyłasz. Accept mówi, co chcesz dostać.

Metody: safe, idempotent i powód, dla którego to ważne

kontrakt z całą siecią

Metoda to nie etykieta, tylko obietnica składana wszystkim pośrednikom. Safe znaczy: klient nie prosi o zmianę stanu. Idempotent znaczy: skutek zamierzony N identycznych żądań jest taki sam jak jednego. Te dwie własności decydują, czy klient, proxy albo biblioteka może bezpiecznie ponowić żądanie po zerwanym połączeniu.

Idempotentność dotyczy stanu serwera, nie odpowiedzi. Drugi DELETE może zwrócić 404, a metoda nadal jest idempotentna. Z drugiej strony GET /orders/7/cancel to mina: robot indeksujący albo prefetch w przeglądarce anuluje zamówienia, bo GET obiecuje bezpieczeństwo.

📌 W punktach
  • Safe ⊂ idempotent. Każda metoda safe jest idempotentna, nie odwrotnie.
  • Ponawiać automatycznie można tylko to, co idempotentne.
  • POST i PATCH potrzebują dodatkowego mechanizmu, żeby ponowienie było bezpieczne.

Statusy: wybieraj semantycznie, nie z przyzwyczajenia

200 z błędem w treści to kłamstwo

Pięć klas: 1xx informacja, 2xx sukces, 3xx przekierowanie, 4xx błąd klienta, 5xx błąd serwera. Rozróżnienie 4xx i 5xx ma konsekwencje operacyjne: 5xx budzi dyżurnego i liczy się do SLO serwisu, a 4xx mówi klientowi „popraw żądanie, ponowienie tego samego nie pomoże”. Wyjątkami są np. 408 i 429, po których ponowienie ma sens.

Nagłówki i negocjacja treści

jeden zasób, wiele reprezentacji

Klient mówi, co akceptuje (Accept, Accept-Language, Accept-Encoding), a serwer wybiera reprezentację. Wartości q określają preferencję: Accept: application/json, text/csv;q=0.5. Gdy wynik zależy od nagłówka żądania, odpowiedź powinna to ogłosić polem Vary, inaczej współdzielony cache poda JSON klientowi, który chciał CSV.

Spring robi to w dwóch miejscach. Atrybuty consumes i produces zawężają mapowanie, więc niedopasowanie kończy się 415 lub 406 przed wejściem do metody. Domyślnie sprawdzany jest tylko nagłówek Accept: dawna strategia rozszerzenia w ścieżce (/orders.json) została usunięta w Spring Framework 7.

@PostMapping(path = "/orders", consumes = MediaType.APPLICATION_JSON_VALUE,
             produces = MediaType.APPLICATION_JSON_VALUE)
public ResponseEntity<OrderDto> create(@RequestBody NewOrder body) { ... }
📌 W punktach
  • Accept niepasujący = 406. Content-Type niepasujący = 415.
  • Odpowiedź zależna od nagłówka żądania wymaga Vary.
  • Spring negocjuje przez Accept, rozszerzenia w URL już nie.

Cache i żądania warunkowe

najszybsze żądanie to to, którego nie ma

Cache HTTP (RFC 9111) to dwa mechanizmy. Świeżość: Cache-Control: max-age=60 pozwala przez 60 sekund nie pytać serwera wcale. Walidacja: po upływie świeżości klient pyta warunkowo, wysyłając If-None-Match z poprzednim ETag. Gdy nic się nie zmieniło, dostaje 304 bez treści.

DyrektywaCo znaczyKiedy użyć
max-age=Nświeże przez N sekunddane mogą być chwilę nieaktualne
s-maxage=Njak max-age, ale dla cache współdzielonychCDN, gateway
no-cachewolno zapisać, ale trzeba walidować przed użyciemzawsze aktualne, a 304 oszczędza transfer
no-storenie zapisywać nigdziedane wrażliwe

Spring daje trzy poziomy. CacheControl buduje nagłówek. WebRequest.checkNotModified(etag) kończy przetwarzanie wcześnie, jeśli klient ma aktualną wersję. Pomija to serializację, a przy tanim ETagu, np. z kolumny version, także ładowanie danych. ShallowEtagHeaderFilter liczy ETag z gotowej treści odpowiedzi: oszczędza pasmo, ale nie CPU, bo odpowiedź i tak powstaje w całości.

@GetMapping("/products/{id}")
public ResponseEntity<ProductDto> get(@PathVariable long id, WebRequest request) {
    String etag = "\"" + service.version(id) + "\"";   // tani odczyt samej kolumny version
    if (request.checkNotModified(etag)) {
        return null;                    // Spring odeśle 304
    }
    ProductDto product = service.find(id);
    return ResponseEntity.ok()
            .cacheControl(CacheControl.maxAge(Duration.ofSeconds(60)))
            .eTag(etag)
            .body(product);
}
⚠️ Uwaga!

no-cache nie znaczy „nie zapisuj”. Do tego służy no-store. To jedna z najczęstszych pomyłek w przeglądach bezpieczeństwa.

📌 W punktach
  • Świeżość oszczędza żądanie, walidacja oszczędza transfer.
  • checkNotModified przy tanim ETagu oszczędza pracę serwera, filtr płytki tylko pasmo.
  • If-None-Match to cache. If-Match to ochrona przed utratą aktualizacji.

HTTP/1.1, HTTP/2, HTTP/3

ta sama semantyka, inne bajty

HTTP/1.1 używa połączeń trwałych, ale na jednym połączeniu odpowiedzi idą po kolei. Dlatego przeglądarki otwierały kilka połączeń naraz. HTTP/2 dzieli wiadomości na binarne ramki i przeplata wiele strumieni w jednym połączeniu TCP, a nagłówki kompresuje przez HPACK. HTTP/3 działa na QUIC, czyli na UDP: strata pakietu blokuje tylko jego strumień, a nagłówki kompresuje QPACK.

W Spring Boot server.http2.enabled ma domyślnie wartość false. Przeglądarki używają HTTP/2 tylko po TLS, więc w praktyce wymaga to certyfikatu albo terminacji na bramie. Twój kod kontrolera nie zmienia się w ogóle, bo semantyka jest taka sama.

❓ Nie ma głupich pytań
Q:
Czyli po przejściu na HTTP/2 mogę sklejać wszystko w jedno połączenie i zapomnieć o puli?
A:
Multipleksowanie usuwa blokowanie na poziomie HTTP, ale w HTTP/2 strata pakietu TCP nadal wstrzymuje wszystkie strumienie tego połączenia. To właśnie naprawia HTTP/3.
📌 W punktach
  • HTTP/2: ramki, strumienie, HPACK, nadal TCP.
  • HTTP/3: QUIC na UDP, strumienie niezależne przy stracie pakietu.
  • Kontrolery Springa nie zależą od wersji HTTP.
Część II

REST: styl architektoniczny, nie format URL

Co naprawdę napisał Fielding i co z tego zostaje w enterprise.

Sześć ograniczeń Fieldinga

REST to zestaw ograniczeń, nie „JSON po HTTP”

REST (Representational State Transfer) opisał Roy Fielding w rozprawie z 2000 roku. To styl architektoniczny dla rozproszonych systemów hipermedialnych, zdefiniowany jako zestaw ograniczeń. Każde ograniczenie kosztuje coś w zamian za konkretną własność całego systemu. Ogranicz, a dostaniesz skalowalność, widoczność i niezależną ewolucję.

Jednolity interfejs ma cztery składowe: identyfikacja zasobów, manipulacja przez reprezentacje, wiadomości samoopisowe i hipermedia jako silnik stanu aplikacji (HATEOAS). Bezstanowość znaczy, że każde żądanie zawiera wszystko, co potrzebne do jego zrozumienia, a stan sesji trzyma klient. Stan zasobów, np. zamówienia, oczywiście żyje w bazie: to nie jest stan sesji.

📌 W punktach
  • Client-server, stateless, cache, uniform interface, layered system, code on demand (opcjonalne).
  • Stan sesji u klienta, stan zasobów na serwerze.
  • REST to styl, a nie standard: nie ma „certyfikatu RESTful”.

Model dojrzałości Richardsona i HATEOAS

poziom 2 to rzeczywistość enterprise

Leonard Richardson opisał cztery poziomy, a Martin Fowler je spopularyzował. To model nauczania, nie norma.

PoziomCo jestPrzykład
0jeden punkt wejścia, HTTP jako tunelPOST /api z nazwą akcji w treści

2metody i statusy zgodne z semantykąGET, PUT, 201, 404
3hipermedia: odpowiedź mówi, co dalejlinki _links.cancel

Większość firmowych API to poziom 2 i jest to rozsądny cel. Poziom 3 daje klientowi odkrywanie akcji i ukrywa zmiany URI, ale kosztuje media type, bibliotekę i klientów, którzy naprawdę podążają za linkami. Spring HATEOAS dostarcza do tego EntityModel, RepresentationModel, WebMvcLinkBuilder oraz format HAL.

EntityModel<OrderDto> model = EntityModel.of(order,
    linkTo(methodOn(OrderController.class).get(order.id())).withSelfRel());
if (order.cancellable()) {
    model.add(linkTo(methodOn(OrderController.class).cancel(order.id())).withRel("cancel"));
}
🔥 Rozmowa przy kominku

Poziom 2: Mój kontrakt jest w OpenAPI. Generujesz klienta i działa.

Poziom 3: A gdy zmienisz regułę „kiedy można anulować”, każdy klient kopiuje ją u siebie. U mnie po prostu nie ma linku.

Poziom 2: Pod warunkiem, że klient w ogóle czyta linki. A zwykle nie czyta.

📌 W punktach
  • Poziom 2 to realistyczny standard enterprise.
  • Linki warunkowe (HATEOAS) mają sens przy złożonych przepływach stanu.
  • Model Richardsona to narzędzie dydaktyczne, nie kryterium zgodności.

Zasoby, reprezentacje, URI

rzeczowniki, nie czasowniki

Zasób to pojęcie, a reprezentacja to jego obecny stan w formacie JSON, XML albo CSV. URI identyfikuje zasób, metoda mówi, co z nim zrobić. Dlatego POST /createOrder dubluje semantykę, a POST /orders ją wykorzystuje.

Identyfikatory publiczne nie muszą być kluczami z bazy. Sekwencyjne ID mogą ułatwiać zgadywanie kolejnych wartości i zdradzać wolumen, dlatego w API publicznym wiele zespołów wybiera UUID. To nie zastępuje autoryzacji, co pokaże rozdział o BOLA.

✏️ Zaostrz ołówek

Zaprojektuj URI dla: listy faktur klienta, pobrania PDF faktury, oraz anulowania faktury.

Odpowiedź

GET /customers/{id}/invoices, GET /invoices/{id} z Accept: application/pdf, a anulowanie to POST /invoices/{id}/cancellation, czyli utworzenie zasobu anulowania. Rozdział o akcjach rozwija tę technikę.

📌 W punktach
  • URI to rzeczowniki w liczbie mnogiej i małymi literami.
  • Zagnieżdżenie maksymalnie jeden poziom, gdy relacja jest własnością.
  • Format wybiera negocjacja, nie rozszerzenie w URI.
Część III

Spring MVC: droga żądania

Jak Spring zamienia bajty HTTP w wywołanie metody i z powrotem.

DispatcherServlet: droga jednego żądania

Front Controller w praktyce

Serwer (domyślnie Tomcat w spring-boot-starter-webmvc) przyjmuje połączenie, parsuje HTTP i przekazuje żądanie przez łańcuch filtrów Servlet do jednego serwletu: DispatcherServlet. To wzorzec Front Controller. Sam niczego nie decyduje, tylko deleguje do strategii, a Boot rejestruje je automatycznie.

Skrót działania: HandlerMapping znajduje metodę i interceptory, HandlerAdapter ją wywołuje, resolvery argumentów budują parametry, a konwertery czytają i zapisują treść. Wyjątek z dowolnego etapu trafia do łańcucha HandlerExceptionResolver.

🤓 Głębiej

@RestController to złożenie @Controller i @ResponseBody. Dzięki @ResponseBody wynik metody nie jest nazwą widoku, tylko trafia do HttpMessageConverter, a ViewResolver w ogóle nie jest używany.

📌 W punktach
  • Filtry Servlet działają przed DispatcherServlet.
  • HandlerMapping wybiera, HandlerAdapter wywołuje.
  • @ResponseBody omija widoki i używa konwerterów.

Kontroler, wiązanie danych, ResponseEntity

cienka warstwa tłumacząca HTTP

Kontroler tłumaczy HTTP na wywołanie domeny. Nie zawiera logiki biznesowej ani transakcji. Oto pełny CRUD z poprawnymi statusami:

@RestController
@RequestMapping("/orders")
class OrderController {

    private final OrderService service;

    OrderController(OrderService service) { this.service = service; }

    @GetMapping("/{id}")
    OrderDto get(@PathVariable long id) {
        return service.find(id);                     // 200, wyjątek domenowy = 404
    }

    @PostMapping
    ResponseEntity<OrderDto> create(@Valid @RequestBody NewOrder body) {
        OrderDto created = service.create(body);
        URI location = ServletUriComponentsBuilder.fromCurrentRequest()
                .path("/{id}").buildAndExpand(created.id()).toUri();
        return ResponseEntity.created(location).body(created);   // 201 + Location
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    void delete(@PathVariable long id) {
        service.delete(id);                          // 204
    }
}

Od Spring Framework 6 /orders/ nie pasuje do mapowania /orders, a w wersji 7 usunięto opcję trailingSlashMatch. Jeśli klienci wysyłają końcowy ukośnik, użyj UrlHandlerFilter albo normalizuj URL na bramie.

  • Kontroler: wiązanie, walidacja, status, DTO. Logika idzie do serwisu.
  • ResponseEntity daje pełną kontrolę nad statusem i nagłówkami.
  • POST tworzący zasób zwraca 201 i Location.

HttpMessageConverter i Jackson 3

bajty w obiekt i z powrotem

HttpMessageConverter to strategia: „umiem czytać ten typ Java z tego media type” i „umiem zapisać go do tego media type”. Spring pyta kolejne konwertery i bierze pierwszy, który pasuje. Dla JSON w Spring Framework 7 jest to JacksonJsonHttpMessageConverter oparty na Jackson 3.

🧰 Z życia wzięte
  1. Nowe pakiety: Jackson 3 żyje w tools.jackson, np. tools.jackson.databind.JsonNode. Adnotacje typu @JsonProperty zostają w com.fasterxml.jackson.annotation.
  2. Bean: Boot 4 konfiguruje JsonMapper i to on jest preferowany. Wsparcie Jackson 2 jest w Spring Framework 7 przestarzałe.
  3. Konfiguracja: właściwości spring.jackson.*, a własne serializatory przez @JacksonComponent.
⚠️ Uwaga!

Zwracanie encji JPA wprost to prośba o kłopoty: leniwe kolekcje, pętle przy relacjach dwukierunkowych i ujawnianie pól. Rozdział o DTO wyjaśnia, dlaczego kontrakt nie może być kopią tabeli.

📌 W punktach
  • Konwerter wybierają typ Java oraz media type.
  • Boot 4 = Jackson 3 = pakiety tools.jackson.
  • Niepoprawny JSON = HttpMessageNotReadableException = 400.

Bean Validation w kontrolerze

🤓 Głębiej

Walidacja składniowa (format, wymagalność) należy do DTO. Reguły biznesowe wymagające stanu, np. „klient ma limit”, należą do domeny i często kończą się 409 lub 422, a nie 400. Grupy walidacji przez @Validated(Group.class) na argumencie pozwalają różnicować create i update, choć dwa osobne DTO są zwykle czytelniejsze.

📌 W punktach

  • Dwa wyjątki MVC do obsłużenia: MethodArgumentNotValidException i HandlerMethodValidationException.
  • Domena pilnuje reguł zależnych od stanu.

PUT kontra PATCH

null to nie to samo co brak pola

PUT zastępuje całą reprezentację, więc pominięte pole znika. PATCH (RFC 5789) wysyła dokument zmian, a format określa Content-Type. Są dwa standardy: JSON Merge Patch (RFC 7396, application/merge-patch+json) i JSON Patch (RFC 6902, application/json-patch+json), czyli lista operacji add, remove, replace, move, copy, test.

Pułapka Javy: rekord z polami String nie odróżnia null od braku pola. Dlatego PATCH często przyjmuje JsonNode i scala go z obecnym DTO, po czym waliduje wynik. Poniższe scalanie jest płytkie: zagnieżdżone obiekty są zastępowane bez @JsonMerge, a null ustawia pole na null. Dla pełnej semantyki RFC 7396 potrzebna jest własna implementacja.

@PatchMapping(path = "/{id}", consumes = "application/merge-patch+json")
OrderDto patch(@PathVariable long id, @RequestBody JsonNode patch) {
    OrderUpdate current = service.currentUpdate(id);
    OrderUpdate merged = mapper.readerForUpdating(current).readValue(patch);
    validator.validate(merged);                 // walidujemy wynik, nie łatkę
    return service.update(id, merged);
}
⚠️ Uwaga!

Merge Patch nie umie ustawić pola na null, bo null oznacza usunięcie. Tablice zastępuje w całości. Jeśli potrzebujesz zmian w środku listy, wybierz JSON Patch albo osobny podzasób.

📌 W punktach
  • PUT: całość. PATCH: zmiana.
  • W Merge Patch null usuwa, a brak pola zostawia.
  • PATCH nie jest z definicji idempotentny.

Idempotency-Key: bezpieczne ponawianie POST

pytanie z początku kompendium

POST nie jest idempotentny, więc utrata odpowiedzi to loteria. Rozwiązanie: klient generuje unikalny klucz (UUID) i wysyła go z żądaniem. Ponowienie używa tego samego klucza. Serwer zapisuje wynik pierwszego wykonania i odtwarza go. Nagłówek Idempotency-Key opisuje szkic IETF httpapi, który nie jest jeszcze RFC.

SytuacjaOdpowiedź według szkicu
brak wymaganego klucza400
ten sam klucz, inna treść422
ten sam klucz, pierwsze żądanie wciąż trwa409
ten sam klucz, ta sama treść, zakończonezapisana odpowiedź

Spring nie ma tego gotowego. Rdzeń to unikalny indeks w bazie, nie sprawdzanie w pamięci: dwa równoległe żądania nie mogą oba przejść. Klucz zapisuje krótka, osobna transakcja, dzięki czemu równoległe żądanie od razu widzi trwające wykonanie i dostaje 409. Skutek biznesowy i wynik zapisuje druga transakcja. Rekord bez wyniku po awarii procesu musi wygasać, inaczej klucz zablokuje się na stałe.

public PaymentResult pay(String key, String fingerprint, PaymentRequest request) {
    // REQUIRES_NEW: INSERT ... ON CONFLICT DO NOTHING, commit od razu
    int inserted = keys.tryInsert(key, fingerprint);
    if (inserted == 0) {
        StoredKey stored = keys.find(key);
        if (!stored.fingerprint().equals(fingerprint)) throw new KeyReusedException();  // 422
        if (stored.result() == null) throw new RequestInProgressException();            // 409
        return stored.result();
    }
    return payments.chargeAndStore(key, request);   // osobna transakcja: skutek + wynik
}
⚠️ Uwaga!

Jeśli obciążenie to zewnętrzne wywołanie, transakcja bazy go nie cofnie. Przekaż ten sam klucz dalej do dostawcy płatności. Idempotencja musi sięgać do końca łańcucha. Ustal też retencję kluczy, np. 24 godziny, i opisz ją w kontrakcie.

📌 W punktach
  • Klucz od klienta, ten sam przy ponowieniu.
  • Unikalny indeks rozstrzyga wyścig.
  • Odcisk treści wykrywa ponowne użycie klucza do czegoś innego.

ETag i @Version: utrata aktualizacji

dwóch edytorów, jeden rekord

Dwóch użytkowników pobiera to samo zamówienie. Obaj edytują. Ostatni zapis nadpisuje pierwszy i nikt nie dostaje błędu. To lost update. Klasyczna odpowiedź HTTP łączy ETag z warunkowym zapisem: If-Match. Po stronie bazy to @Version z JPA.

@PutMapping("/{id}")
ResponseEntity<OrderDto> put(@PathVariable long id,
        @RequestHeader(name = HttpHeaders.IF_MATCH, required = false) String ifMatch,
        @Valid @RequestBody OrderUpdate body) {
    if (ifMatch == null) {
        return ResponseEntity.status(HttpStatus.PRECONDITION_REQUIRED).build();  // 428
    }
    long version = Long.parseLong(ifMatch.replace("\"", ""));
    OrderDto saved = service.update(id, version, body);     // porównuje wersję
    return ResponseEntity.ok().eTag("\"" + saved.version() + "\"").body(saved);
}

Serwis porównuje wersję z żądania i rzuca wyjątek mapowany na 412. Sam @Version chroni dodatkowo przed wyścigiem w krótkim oknie między odczytem a zapisem: dostawca JPA sprawdza wersję przy zapisie, a Spring zgłasza OptimisticLockingFailureException, którą advice mapuje na 412 lub 409.

📌 W punktach
  • GET zwraca ETag, PUT wysyła If-Match.
  • Niezgodność = 412, brak warunku = 428.
  • @Version domyka okno wyścigu w bazie.

Transactional outbox i webhooki

baza i broker nie mają wspólnej transakcji

Zapis do bazy i publikacja zdarzenia to dwa systemy. Jeśli publikujesz w transakcji, a commit się nie uda, wysłałeś kłamstwo. Jeśli po commicie i aplikacja padnie, zdarzenie przepadło. Outbox zapisuje zdarzenie do tabeli w tej samej transakcji, a osobny relay publikuje je dalej. Gwarancja to at-least-once, więc konsumenci muszą deduplikować po identyfikatorze zdarzenia.

@Transactional
public OrderDto create(NewOrder body) {
    Order order = orders.save(Order.from(body));
    outbox.save(OutboxEvent.orderCreated(order));   // ta sama transakcja
    return OrderDto.from(order);
}

Webhook to odwrócony kierunek: twój serwis wywołuje klienta. Podpisz treść HMAC, dodaj znacznik czasu przeciw replay, ponawiaj z rosnącym opóźnieniem i udostępnij identyfikator zdarzenia. Odbiorca powinien odpowiedzieć szybko, a pracę wykonać asynchronicznie.

🤓 Głębiej

@TransactionalEventListener(phase = AFTER_COMMIT) uruchamia kod po commicie, ale jeśli proces padnie zaraz potem, zdarzenie zniknie. Do gwarancji dostarczenia potrzebna jest trwała tabela.

📌 W punktach
  • Outbox: dane i zdarzenie w jednej transakcji.
  • At-least-once wymaga idempotentnych konsumentów.
  • Webhook: podpis, ponowienia, deduplikacja.

API Gateway i BFF

sprawy przekrojowe na brzegu

Gateway to wspólny punkt wejścia: TLS, routing, limity, uwierzytelnianie wstępne. BFF (Backend for Frontend) to API dopasowane do jednego klienta, np. aplikacji mobilnej, składające dane z kilku usług. W ekosystemie Springa bramę realizuje Spring Cloud Gateway.

Za proxy aplikacja widzi adres bramy, nie klienta, więc linki w Location mogą wskazywać zły host. Rozwiązanie to nagłówki X-Forwarded-* lub Forwarded oraz właściwość server.forward-headers-strategy z wartościami native, framework lub none.

⚠️ Uwaga!

Nagłówki przekazywane mogą zostać podrobione przez klienta. Włączaj ich obsługę tylko wtedy, gdy zaufane proxy na brzegu je usuwa i ustawia na nowo. Dokumentacja Springa ostrzega przed tym wprost przy ForwardedHeaderFilter.

📌 W punktach
  • Gateway dla spraw przekrojowych, nie logiki biznesowej.
  • BFF, gdy klienci mają bardzo różne potrzeby.
  • server.forward-headers-strategy tylko za zaufanym proxy.

Odporność: timeout, retry, circuit breaker

jak zatrzymać kaskadę awarii

Wolna zależność jest gorsza niż martwa: wątki czekają, pula się wyczerpuje i pada serwis, który sam był zdrowy. Kolejność obrony: timeout (zawsze), retry z backoffem i jitterem (tylko operacje idempotentne), limit współbieżności, circuit breaker.

Od Spring Framework 7 retry i limit współbieżności są w rdzeniu. Włączasz je przez @EnableResilientMethods. Domyślnie @Retryable ponawia dla każdego wyjątku do 3 razy, z sekundą przerwy. Circuit breakera w rdzeniu nie ma, więc tutaj używa się Resilience4j.

@Configuration
@EnableResilientMethods
class ResilienceConfig { }

@Retryable(includes = HttpServerErrorException.class,
           maxRetries = 3, delay = 200, multiplier = 2, jitter = 50)
@ConcurrencyLimit(20)
public Stock find(String sku) { ... }
⚠️ Uwaga!

@Retryable bez includes ponowi też 400 i 404, czyli błędy, których ponowienie nie naprawi. Retry na wielu warstwach mnoży ruch: trzy warstwy po trzy próby to dziesiątki wywołań na żądanie w najgorszym momencie. Ponawiaj w jednym miejscu.

📌 W punktach
  • Zawsze connect i read timeout.
  • Retry tylko dla idempotentnych operacji i błędów przejściowych.
  • Breaker przerywa ruch do chorej zależności i daje jej czas.

OAuth2 Resource Server i JWT

API weryfikuje, nie wystawia

W OAuth2 token wystawia serwer autoryzacji, a API to resource server: sprawdza podpis i claimy. Spring Security robi to przez BearerTokenAuthenticationFilter, JwtDecoder i JwtAuthenticationConverter.

spring.security.oauth2.resourceserver.jwt.issuer-uri=https://idp.example.com/issuer
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(a -> a
            .requestMatchers("/actuator/health/**").permitAll()
            .requestMatchers(HttpMethod.POST, "/orders").hasAuthority("SCOPE_orders:write")
            .anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .csrf(c -> c.disable())                     // tylko bez ciastek uwierzytelniających
        .build();
}

Domyślnie resource server waliduje podpis oraz exp, nbf i iss, a każdy scope zamienia w uprawnienie z prefiksem SCOPE_. Warto dodać walidację aud: token wystawiony dla innego API nie powinien tu działać (RFC 8725).

⚠️ Uwaga!

Typowy JWT jest podpisany (JWS), ale nie zaszyfrowany. Nie umieszczaj w nim danych wrażliwych. Resource server, który sprawdza tylko podpis i claimy, nie dowie się o unieważnieniu tokenu przed exp, więc czas życia powinien być krótki.

📌 W punktach
  • API jest resource serverem, a tokeny wystawia IdP.
  • issuer-uri wystarczy do konfiguracji.
  • Sprawdzaj aud, trzymaj krótkie exp.

CORS i CSRF

przeglądarka, nie serwer, egzekwuje CORS

CORS rozluźnia politykę same-origin w przeglądarce. Nie chroni serwera: curl go ignoruje. Żądania niebędące prostymi poprzedza preflight, czyli OPTIONS z Origin i Access-Control-Request-Method.

@Bean
UrlBasedCorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("https://app.example.com"));
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "PATCH", "DELETE"));
    config.setAllowedHeaders(List.of("Authorization", "Content-Type", "If-Match"));
    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", config);
    return source;
}

CORS musi działać przed Spring Security, bo preflight nie ma danych uwierzytelniających i dostałby 401. Spring Security konfiguruje to samo, jeśli znajdzie bean UrlBasedCorsConfigurationSource. Ogólnie masz też @CrossOrigin i addCorsMappings.

CSRF wykorzystuje to, że przeglądarka dokleja ciastka sama. Token w nagłówku Authorization nie jest dołączany automatycznie, więc API z tokenem Bearer może wyłączyć ochronę CSRF. API z ciastkiem sesyjnym nie może.

📌 W punktach
  • CORS to reguła dla przeglądarki, nie autoryzacja.
  • Preflight musi przejść przed uwierzytelnianiem.
  • Ciastka = CSRF. Bearer w nagłówku = bez CSRF.

Strategie DispatcherServlet

wszystko jest wymienne

Wewnątrz RequestMappingHandlerAdapter działają dwie listy strategii. HandlerMethodArgumentResolver buduje każdy argument metody, a HandlerMethodReturnValueHandler obsługuje wynik. @RequestBody to jeden z resolverów, a @ResponseBody jeden z handlerów. Oba delegują do konwerterów.

@Target(ElementType.PARAMETER)
@Retention(RetentionPolicy.RUNTIME)
public @interface CurrentTenant { }

class TenantResolver implements HandlerMethodArgumentResolver {
    @Override
    public boolean supportsParameter(MethodParameter parameter) {
        return parameter.hasParameterAnnotation(CurrentTenant.class);
    }
    @Override
    public Object resolveArgument(MethodParameter parameter, ModelAndViewContainer mavContainer,
                                  NativeWebRequest webRequest, WebDataBinderFactory binderFactory) {
        return webRequest.getHeader("X-Tenant");
    }
}

@Configuration
class WebConfig implements WebMvcConfigurer {
    @Override
    public void addArgumentResolvers(List<HandlerMethodArgumentResolver> resolvers) {
        resolvers.add(new TenantResolver());
    }
}

Health probes i graceful shutdown

wdrożenie bez utraconych żądań

Boot udostępnia /actuator/health/liveness i /actuator/health/readiness. Liveness odpowiada na pytanie: czy trzeba zrestartować proces? Readiness: czy wolno kierować ruch?

⚠️ Uwaga!

Nie dodawaj bazy do liveness. Awaria bazy zrestartuje wszystkie pody jednocześnie, a to niczego nie naprawi. Zależności zewnętrzne mogą co najwyżej wpływać na readiness.

Graceful shutdown jest domyślny: server.shutdown=graceful i spring.lifecycle.timeout-per-shutdown-phase=30s. Po SIGTERM serwer kończy trwające żądania i nie przyjmuje nowych. W Kubernetesie dodaj krótki preStop, bo usunięcie poda z endpointów dzieje się równolegle i przez chwilę ruch nadal może przychodzić.

📌 W punktach
  • Liveness: tylko stan procesu.
  • Readiness: gotowość na ruch.
  • terminationGracePeriodSeconds dłuższy niż timeout zamykania.

  • URI to rzeczowniki, spójne nazewnictwo w całej firmie.
  • Metody zgodne z semantyką: GET nic nie zmienia.
  • OpenAPI w repozytorium, a diff w CI.
  • Błędy w application/problem+json.
  • Statusy: 201 z Location, 204 bez treści, 4xx kontra 5xx.

Kolekcje i zmiany

  • Limit rozmiaru strony i białe listy sortowania.
  • Stabilny JSON strony (PagedModel, VIA_DTO).
  • Współbieżne zapisy chronione: If-Match, @Version.
  • POST z efektem finansowym ma Idempotency-Key.
  • Długie operacje przez 202.

Spring

  • DTO zamiast encji, open-in-view=false.
  • @RestControllerAdvice obsługuje wyjątki MVC i Exception.
  • Oba wyjątki walidacji obsłużone.
  • Logika w serwisach, transakcje poza kontrolerem.

Bezpieczeństwo

  • Autoryzacja obiektowa na każdym ID.
  • aud, iss, krótkie exp.
  • Rate limit, limity uploadu i strony.
  • Brak danych wrażliwych w URL i logach, no-store dla nich w odpowiedzi.
  • CORS z jawną listą origin.

Odporność i produkcja

  • Każdy klient ma connect i read timeout.
  • Retry tylko dla operacji idempotentnych, w jednej warstwie.
  • Liveness bez zależności zewnętrznych.
  • Metryki, ślady, logi z traceId.
  • Polityka wersji i wycofywania z Deprecation i Sunset.

Testy

  • Slice web dla ścieżek błędów i walidacji.
  • Test „inny użytkownik” dla każdego zasobu.
  • Testcontainers zamiast H2.
  • Kontrakty na granicach zespołów.
